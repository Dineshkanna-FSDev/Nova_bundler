# Nova: Layered Cache Architecture & Design

> **Specification Version:** 3.0  
> **Status:** Architecture Reference & Specification Document  
> **Crate:** `crates/nova-cache`

---

## 1. Overview & Objectives

In modern development workflows, 95% of build cycles are **incremental rebuilds** where fewer than 5 files change out of thousands. In traditional bundlers, a single file change often triggers expensive re-parsing, full-graph re-evaluations, or broad bundle re-concatenation.

Nova implements a **content-addressable, multi-tier, stage-specific cache system** designed to satisfy three core requirements:
1. **Sub-millisecond Cache Lookups:** Direct memory-mapped access and lock-free concurrent hash lookups.
2. **Deterministic Invalidation:** Zero false cache hits; invalidations are strictly determined by content cryptographic fingerprints.
3. **Stage Decoupling:** Modifying an implementation file without changing its exports invalidates only its local IR and downstream chunk, leaving the ASTs, dependency graph, and other chunks untouched.

## 3. Dedicated Cache Stores

| Cache Store | Directory Path | Artifact Stored | Key Formulation |
|---|---|---|---|
| **AST Cache** | `.nova/cache/ast/` | Serialized syntax tree | $\text{BLAKE3}(\text{SourceBytes} \parallel \text{ParserVersion})$ |
| **Binary IR Cache** | `.nova/cache/ir/` | Pre-compiled `.novair` bytecode | $\text{BLAKE3}(\text{AST\_Hash} \parallel \text{CompilerConfig})$ |
| **Dependency Graph Cache** | `.nova/cache/graph/` | Graph adjacency & symbol maps | $\text{BLAKE3}(\text{WorkspaceManifest} \parallel \text{AllIRKeys})$ |
| **Optimization Result Cache** | `.nova/cache/opt/` | Transformed Binary IR | $\text{BLAKE3}(\text{IR\_Hash} \parallel \text{PassFlags})$ |
| **Asset Cache** | `.nova/cache/assets/` | Compressed SVGs, images, CSS | $\text{BLAKE3}(\text{RawAssetBytes} \parallel \text{CompressionLevel})$ |
| **Bundled Chunk Cache** | `.nova/cache/chunks/` | Final minified `.js` & `.map` chunks | $\text{BLAKE3}(\sum \text{MemberIRHashes} \parallel \text{BundlerConfig})$ |

## 4. Key Formulation & Hashing Mechanics

Nova exclusively standardizes on **BLAKE3** for all fingerprinting:
- **Throughput:** BLAKE3 processes source text at over 5 GB/s per core on modern x86-64 and ARM64 CPUs.
- **Tree Hashing:** Enables incremental hashing of massive multi-megabyte files without reading the entire file into contiguous RAM.

### Cache Key Composition Formula

For any compilation stage $S$ operating on module $m$:

$$\mathcal{K}_{\text{stage}}(m) = \text{BLAKE3} \Big( \mathcal{H}_{\text{input}}(m) \;\parallel\; \text{StageId}(S) \;\parallel\; \mathcal{H}_{\text{config}}(S) \;\parallel\; \text{EngineVersion} \Big)$$

## 5. Cache Eviction & Space Management

Without active quota management, local disk caches grow indefinitely. Nova implements an automated background maintenance worker:

### 5.1. Least Recently Used (LRU) Eviction
- Every cache entry maintains an access timestamp in its file metadata.
- When total disk cache exceeds the configured threshold (default: `2.0 GB`), the cleanup routine evicts the oldest entries until disk consumption drops below 75% of the quota.

### 5.2. Garbage Collection Sweeps
- At the start of a cold build, orphaned cache entries whose parent source files no longer exist on disk are purged.
- Stale version entries generated by older Nova engine releases are automatically invalidated and deleted.

## 6. Disk Layout

```text
.nova/
└── cache/
    ├── manifest.json       # Cache index metadata and LRU access log
    ├── ast/                # Serialized AST blobs (keyed by hash)
    │   ├── 4a/
    │   │   └── 4a8e2b...ast
    ├── ir/                 # Compiled Binary IR (.novair)
    │   ├── 9f/
    │   │   └── 9f12d0...novair
    ├── graph/              # Dependency graph topology
    │   └── graph_v3.bin
    ├── opt/                # Optimization pass artifacts
    │   └── 3c/
    │       └── 3ca40f...opt
    └── chunks/             # Compiled JS chunks
        └── 8b/
            ├── 8b71d9...js
            └── 8b71d9...js.map
```
